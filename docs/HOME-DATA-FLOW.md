# 首页的数据是怎么来的

首页文件只有 20 行，但它是整个 App 里最值得看的一处结构：
**两条互不相干的流**，一条决定「用哪套设计画」，一条决定「画什么数字」，
只在最后一行汇合。

## 全景图

```
        选哪套设计                            画什么数字
   ───────────────────               ───────────────────
   点「我的 → 首页布局」                   本地 SQLite
          │                                    │
          ▼                                    ▼
   存进 store（内存，界面立刻变）        db/ 里的 SQL：求和、按分类分组
   + 写进手机存储（下次启动还在）              │
          │                                    ▼
          ▼                              React Query 包一层（缓存）
   layoutName: 'pace' | 'ring'                 │
          │                                    ▼
          │                        use-home-view-data：日均、快慢、按天分组
          │                              ← 唯一算数字的地方
          │                                    │
          │                                    ▼
          │                              data: HomeViewData
          │                                    │
          └──────────────┬─────────────────────┘
                         ▼
       layoutName === 'ring' ? <RingLayout data/> : <PaceLayout data/>
                         ▼
                 布局组件只管把 data 画出来
```

首页全文就是三行加一个三元表达式：

```tsx
const theme = useTheme();
const layoutName = useHomeLayout();     // 左边这条流的终点
const data = useHomeViewData();         // 右边这条流的终点
```

关键在于：**选哪套布局不影响取什么数，取出来的数也不知道自己会被谁画。**
两套布局收的参数完全一样，所以可以互换。加第三套 = 新建一个组件文件 + 注册两行，
取数那边一个字都不用动。

## 左边：选了哪套布局

首页只盯着 `layoutName` 这一个值：

- 在设置页点「金环」→ 这个值变了 → 首页重画 → 换成另一个组件。**整个过程一次数据库都不查**
- store 里别的字段变了，首页不受影响

写入是「内存先改、磁盘随后」：界面立刻就变，写进手机存储是后台做的，只影响下次冷启动。

### 为什么冷启动不会先闪一下默认布局

根布局那里有一道门：三个 store（登录状态、主题、布局）都从手机存储读完了才放行，
读完之前什么都不画。所以首页第一次渲染时，拿到的已经是用户上次选的那套。

**以后加任何一个需要记住的偏好项，都要记得往这道门里加一个条件**，否则就会闪。

## 右边：数字

分四层，每层只干一件事：

| 层 | 在哪 | 干什么 |
|---|---|---|
| 存 | 本地 SQLite | 数据的唯一来源 |
| 查 | `db/transactions.ts` `db/budgets.ts` | 写 SQL，求和、分组 |
| 缓存 | `hooks/use-transactions.ts` `hooks/use-budgets.ts` | React Query 包一层：缓存、失效、加载状态 |
| 算 | `hooks/use-home-view-data.ts` | 把三份查询结果算成首页要的那一份数据 |

容易误解的一点：**用 React Query 不是因为要发网络请求**。数据就在本机，
用它纯粹是为了拿到「缓存 + 失效」这套机制，省掉自己管一堆 useState 和 useEffect。

### 为什么数字必须集中算一次

日均消费、预算比时间快多少、按天分组——**这些库里一个都没存，全是算出来的**。

如果让每套布局各算各的，早晚出现「切到金环布局，日均变成了 113.74」这种 bug。
两处四舍五入的时机差一点就够了，而且这种 bug 没人查得出来，因为两处代码看起来都对。

所以规矩是：**算「事实」只能在一个地方算。**

但不是说组件里一行算术都不许写，要分清是哪一种：

```tsx
// ❌ 这是在算事实，必须挪到统一的地方
const dailyAverage = spent / daysElapsed;

// ✅ 这是在决定怎么显示，留在组件里没问题
<ThemedText>已用 {Math.round(percentage)}%</ThemedText>
```

**界线就是一个问题：两套布局在这里算出不一样的结果，是 bug 还是设计选择？**

- 日均是多少 → **事实**。两套算出不同的值就是 bug，必须统一算
- 显示成 `71%` 还是 `70.8%` → **显示形式**。两套精度不同是设计选择，留在组件里

### 为什么拆成一个 hook 和一个普通函数

`use-home-view-data.ts` 导出两个东西：

- `buildHomeViewData(输入)` —— 普通函数，不碰 React，给定输入永远给出同样的输出
- `useHomeViewData()` —— 薄薄一层，负责调三个查询，把结果喂给上面那个函数

拆开是为了留一个能测的入口：以后要给「预算快慢」这类规则写测试，
喂一组假数据给普通函数就行，不用渲染任何组件、不用起数据库。

## 反过来：记了一笔之后首页怎么更新

写进 SQLite → 把相关的缓存**全部**标记成过期 → React Query 重新查库 → 首页拿到新数据重画。

缓存是一把梭全部失效、不精确挑，这是故意的：一笔账会同时影响账单列表、月度汇总、
标签汇总、报销清单和账户余额，**挑漏了就会出现「记了一笔但首页数字没变」**——
这种 bug 的排查成本，远高于多跑几次本地查询的成本。

布局组件在这条流里完全是被动的，它甚至不知道刚刚发生过一次写入。

## 一句话总结

- 一条流送**数据**（SQLite → SQL → 缓存 → 集中算一次）
- 一条流送**选择**（点一下 → store → 存进手机）
- 它们只在最后一行汇合，之后的组件只负责画

要加布局动左边，要加数字动右边，两边互不影响——这就是这个结构存在的全部理由。

# 附录：`src/` 每层各管什么

新写一个文件不知道放哪时，看这一节。

| 目录 | 回答的问题 | 判断标准 |
|---|---|---|
| `db/` | 数据在本地怎么存、怎么查 | **唯一允许出现 SQL 的地方**，别处看到 `SELECT` 就是越界 |
| `api/` | 跟服务器怎么来回 | 发网络请求的都在这里 |
| `store/` | 跨页面共享、而且要记住的**选择** | 两条同时满足：多个页面要读；不是从库里查出来的 |
| `hooks/` | 组件要用这些东西时怎么拿 | 用到了 React，而且要被多个组件复用 |
| `constants/` | 写死的配置 | 纯数据，没有逻辑，跑起来之后永远不变 |
| `utils/` | 跟业务和 React 都无关的普通函数 | 输入一样输出永远一样 |
| `components/` | 长什么样 | 会返回 JSX |

`db/` 和 `api/` 是对称的两层：一个管本机数据库，一个管服务器。按「本地优先」这条原则，
`db/` 是主力，`api/` 目前只管登录，以后的同步逻辑会长在这里。

## 最容易混的两组边界

### `store/` 不是「存数据」的地方，数据库才是

分清两个词：

- **数据**（交易、分类、账户）→ 进 **SQLite**。它是事实，可能有上万条，要用 SQL 算，关机不能丢
- **选择**（当前登录的是谁、选了哪套主题、哪套布局）→ 进 **store**。就一个值，没人会拿它做统计

而且 **store 本身是内存，App 关掉就没了**。布局那个 store 其实同时做了两件事：
往内存里写一份（界面立刻变），再写一份到手机存储（下次启动还在）。
**真正"存"下来的是手机存储，不是 store。**

判断一个东西放哪，问三个问题：

```
关掉 App 再打开，它应该还在吗？
├── 不该在（输入框里还没提交的草稿）  → 组件自己的 useState
└── 该在
    ├── 是事实、可能很多条、要查要算  → db/
    └── 只是一个选择、就一个值        → store/ + 写进手机存储
```

### `constants/` vs `utils/`：是「数据」还是「动作」

配色表是一张表 → `constants/`；`formatAmount()` 是一个动作 → `utils/`。

## 新文件放哪：从上往下问，撞到哪条停哪条

```
要写 SQL 吗？                        → db/
要发网络请求吗？                      → api/
是一张写死的表、永远不变吗？           → constants/
是普通函数，不碰 React 也不碰数据库吗？ → utils/
是跨页面共享 + 要记住的用户选择吗？     → store/
用到了 React 且要被多个组件复用吗？     → hooks/
会画出东西吗？                        → components/
```

**顺序不能换。** 比如 `formatAmount` 也能包成一个 hook，但它根本不需要 React——
先撞到 `utils/` 那条就该停下。能不引入 React 就不引入，普通函数永远比 hook 好测、好复用。

`components/` 内部怎么再分，见 `CLAUDE.md` 里那两条归类规则。
