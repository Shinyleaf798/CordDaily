# 项目规格文档

这份文档说的是「这个 App 应该长什么样、数据怎么存、接口有哪些」。
**改需求或加功能，先改这份文档，再动代码。**

数据表的精确定义（字段类型、默认值、关系）在 `backend/prisma/schema.prisma`，
那份文件才是准的。这里只用大白话说每张表存什么、为什么这么存。

## 1. 要做的功能

| 模块 | 功能 |
|---|---|
| 认证 | 注册、登录、登出 |
| 记账 | 新增 / 编辑 / 复制 / 删除一笔账（主题、备注、金额、币种、汇率、分类、账户、日期时间、标签、图片） |
| 分类 | 两级分类（父 + 子），增删改；图标可以是表情、内置图片，或者传一张自己的图——**相册和文件两个入口**（下载来的 logo 在 `Download/`，系统相册选择器看不见它），自动缩到 192px 存进沙盒，跟着备份包和云端一起走；被账单用着的分类不许删，但可以「停用」——从记账页收起来，历史账单照常统计；一级分类可以长按拖动，决定它在记账页网格里的先后 |
| 账户 | 一组付款方式的名字（现金 / TNG / 某张卡），记账时选一个。只有名字，没有余额，也没有账户之间的转账 |
| 预算 | 一个月度总预算：填一个数，跟当月全部支出比；超了就提醒，在手机本地实时算 |
| 周期性交易 | 设一条规则（多久一次 / 多少钱 / 什么分类 / 哪个账户），App 打开时本地补生成 |
| 同步 | 数据存在手机本地。自动同步**默认关**，用户自己开、自己选周期（每天 / 每 7 天 / 每月）；也可以随时手动点「备份到云端」。只往服务器推，不往回拉 |
| 备份与恢复 | 导出成文件（完整备份 `.json` 给 App 自己、表格 `.csv` 给 Excel），或从文件恢复；重装后首次登录问一次要不要从云端恢复。恢复**只增不删** |
| 统计（手机端） | 本月支出 + 环比、按分类的支出构成、标签汇总、待收回 |
| 统计（电脑端） | 月度收支趋势图、分类占比图、预算完成情况，全部只读 |

## 2. 数据表

一共 8 张表。

| 表 | 存什么 |
|---|---|
| 用户 | 邮箱、加密后的密码、本位币（默认 MYR） |
| 分类 | 名字、图标、收/支、属于谁；有一个「父分类」字段，为空就是一级分类；还有排列顺序和「是否启用」两个字段。内置分类的 id 是写死的常量，每台设备一样（见下面的取舍） |
| 账户 | 名字、币种。`openingBalance` 和 `type` 两列还在但**已经不用了**（见下面的取舍） |
| 交易 | 一笔账的全部信息，见下面详细说明 |
| 交易图片 | 一个图片网址，挂在某笔交易下面 |
| 周期规则 | 多久一次、下次该生成的日期、开始和结束日期、是否启用 |
| 转账 | 从哪个账户、到哪个账户、多少钱、哪天。**表建了但一直是空的**，账户降级成纯标签之后也不会再做 |

### 交易表里几个需要解释的字段

| 字段 | 干什么用 |
|---|---|
| 主题 | 这笔账是为了什么事。跟分类、金额一起是保存的三个硬门槛，其余字段（备注、店名、地点、标签）空着也能存。老账单里可能存着当初从店名或分类名自动顶上的值 |
| 店名 / 地点 | 会被反复输入的值（麦当劳、吉隆坡机场），所以做历史补全 |
| 备注 | 这一笔特有的明细（「3个汉堡2个薯条」），每笔都不一样，不做补全 |
| 币种 / 汇率 / 折算后金额 | 一笔外币账存三个数：收据上那个数（500 日元）、记账那一刻的汇率、折算成林吉特是多少。汇率**存下来就不再变**，之后涨跌都不影响历史账单。所有加总（统计、预算、当天小计、SQL 里的 SUM）一律加折算后的那个值——两个币种的数字直接相加得不出任何东西 |
| 标签 | 跟分类平行的另一个汇总角度。一趟旅行横跨机票、餐饮、购物，只有标签圈得起来 |
| 可报销 + 收回时间 | 两个字段是两个状态：收回时间为空 = 还没收回，有值 = 已经收回 |
| 不计入统计 | 钱动了但不算「我的消费」（帮人垫付、一次性大额）。首页、预算和统计页的构成图都跳过它 |

### 关键取舍

- **折算后的金额在记账时就算好**：汇率是用户当时自己查了填的，跟这笔账绑死，不是事后能用「今天的汇率」重算的东西。顺带也省了每次统计都要换算
- **id 由手机端生成**：手机离线创建的那一刻 id 就定了，同步时靠它判断「这笔是不是已经推过了」，网络重试不会存成两份
- **内置分类的 id 是写死的常量**：默认分类原来是装 App 那一刻现场生成 UUID 的，于是重装之后新手机上的「餐饮」跟备份里的「餐饮」名字一样、id 不同——那批账单要么存不进去（服务器的外键），要么静默变成一堆点开是空白的行（本地 `foreign_keys` 是关着的）。写死之后，恢复时绝大多数行的 id 根本不用动，连用户改过的名字、停用状态都跟着回来。必须是**合法 UUID 格式**（后端 `z.string().uuid()` 会打回 `builtin-food` 这种），而且**发布之后永不修改**——地位等同于一条已发布的迁移
- **内置分类不在代码里开特例**：它只是「一个恰好每台设备都相同的 id」。同步、备份、排序、改名、停用全部走跟自建分类完全一样的路径。曾经考虑过在云端分两张表（内置一张、自建一张），放弃了：这批分类是**可以被用户改名、停用、挪层级、拖排序**的，一张全用户共享的只读表装不下这些编辑；而且排序要跨两张表 UNION、交易的外键没法同时指向两张表。至于「自建分类可以上传图片」这层因素，`icon` 字段本来就同时装得下 `🍜`、`builtin:food` 和图床 URL（见下一条），不需要靠建表来区分
- **服务器上 `Category` / `Account` 的主键是 `@@id([userId, id])`**：内置分类的 id 在所有用户之间共享，全局唯一的主键装不下第二个用户的那 13 行。交易那边的关系跟着改成 `[userId, categoryId] → [userId, id]`（`Transaction` 本来就有 `userId`，不用加列），外键、`GROUP BY` 统计、电脑端只读全都不受影响
- **「停用」是被引用的分类唯一的出路**：删分类的规则是「还有账单在用就不许删」，可现实里分类只会越攒越多——没有第二条路，记账页的网格就只增不减。停用（`isActive = false`）把它从记账页收起来，历史账单、统计、下钻一个字都不变，随时能放回去。所以永久删除只对「一笔都没用过」的分类开放，其余一律引导到停用
- **子分类跟着父分类一起藏**：一个子分类在记账页只能从它的父分类点进去，父分类停用了，子分类就没有入口。这个「藏起来」是**每次读的时候算出来的**（父启用 且 自己启用），不往子分类行上写状态——写进去的话，父分类一停一启就要级联改一批行，还得记住哪些子分类本来就是用户自己停掉的
- **分类顺序只排一级**：`sortOrder` 每一行都有，但界面只让拖一级分类。子分类跟着创建顺序走——「早餐排在午餐前面」几乎没人在意，而两层嵌套的拖拽是这个功能里最难写的一块。列全都留着，哪天想开子分类排序不用再迁移一次
- **分类图标是一个带前缀的字符串，不拆成两列**：三种写法共用一个字段——表情（`🍜`）、内置图片（`builtin:food`）、用户自己上传的图（`custom:a1b2.jpg`）。没有任何查询要按图标类型过滤，拆成两列只会让每张表、每次同步都多一个字段。三种存的都是**引用**不是位置：内置的换图、改文件名都不用动数据库；上传的只存文件名，目录运行时现算，iOS 换沙盒容器之后照样对得上。上传的图片本体不进数据库，放沙盒的 `category-icons/`，并以 base64 跟着备份包走（包要自解释）。清理靠「每次写分类后拿数据库对一遍目录」，不在每个出口各删一次。云端那条路**也带图**：备份时图片本体传到 `/category-icons/batch` 存进 Neon，恢复时跟着 `/sync/bundle` 回来，所以重装 + 从云端恢复之后自定义图标还在。存 Neon 而不是图床，是对「图片只存网址」的一次有意破例，范围只限分类图标（账单收据照片仍走 Cloudinary）——分界线是量，见第 4 节接口清单下面那段
- **预算只有一个总数，不按分类设**：口径是「本月全部支出（跳过『不计入统计』的）vs 那个数」。按分类设过一版，颗粒度太细、录入成本高于它带来的信息量，整个删掉了
- **预算存在手机本地的设置表里，不进服务器**：它是一个偏好值不是账目数据。代价是**云端恢复带不回它**——但完整备份文件会把它一起带走，所以文件备份仍然是唯一完整的快照。要让云端也带上，得先给服务器加一张设置表，那是后面的事
- **账户没有余额**：曾经是「不存、每次现算」（余额 = 期初 + 收支和转账的汇总）。现在连算都不算了——手机端不显示，那套计算只留在后端给以后的电脑端用
- **没有资产页**：账户在这个 App 里只有一个职责——让一笔账能记下「我用什么付的」。既然余额准不准无关紧要，就不需要转账、不需要对账，整页只剩三五个名字，撑不起一个底部 tab。账户管理降级到「我的 → 账本」，跟分类管理做邻居；空出来的 tab 位给了统计页。`accounts` 表上的 `openingBalance` 和 `type` 两列留着不用（删列要整表重建），后端的余额计算也留着——电脑端只读，那套算法本身没错
- **账户没有分类，也没有类型**：账户存在的唯一目的是给一笔账贴上「我用什么付的」（现金、TNG、某张卡）。再给这些标签分一次类，在只有两三个账户时是纯仪式感。表上的 `type` 列留着恒为 `OTHER`、`openingBalance` 恒为 0——删列要整表重建，留两个没人读的列不碍事
- **周期规则和转账都是独立的表**：规则是「规则」，它生成的每一笔仍然是正常的交易；转账不计入收支统计，所以不混进交易表
- **图片只存网址**：图片本身直传图床，后端和数据库都不碰二进制
- **交易表留了一个「最后修改时间」**：现在电脑端只读用不上，但先加着，以后做网页编辑时可以用「谁改得晚听谁的」来处理冲突
- **只在两处加级联删除**：删用户时自动清掉他名下所有数据（为以后的注销账号准备）；删交易时自动清掉它的图片。其余关系一律是「还有账单在用就不许删」，避免「删个分类，几十笔账跟着消失」

## 3. 登录怎么做

- **登录是可选的**。App 启动直接进主界面，没有登录门：记账、统计、导出文件、从文件恢复都不需要账号。只有云端那三件事（备份到云端、从云端恢复、自动同步）会要求先登录，入口在「我的 → 账号」
- 注册时密码加密存，数据库里没有明文
- 登录返回两个凭证：一个 15 分钟过期的（每次请求带它），一个 7~30 天的（用来换新的那个）
- 短的过期了自动用长的换一个新的，用户不用重新登录
- 手机端把凭证存在系统的安全存储里

## 4. 接口清单

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/auth/register` | 注册 |
| POST | `/auth/login` | 登录，返回两个凭证 |
| POST | `/auth/refresh` | 换一个新的短期凭证 |
| GET | `/auth/me` | 当前登录的是谁 |
| GET/POST | `/categories` | 分类：查 / 新建。POST **收手机传来的 `id`** 并按 `(userId, id)` upsert——不收的话服务器会自己生一个，手机推上来的账单就会指向一个服务器上不存在的分类 |
| PUT/DELETE | `/categories/:id` | 分类：改 / 删 |
| GET | `/category-icons` | 云端已经存了哪几张自定义分类图标，**只回名字不回图**。手机端据此决定这次要传哪几张，于是本地不用记一份会走散的上传台账 |
| POST | `/category-icons/batch` | 把图片本体（base64）传上去，一批最多 20 张。同名的直接跳过——文件名是 UUID，换图就换名，同名必然同图。存进 Neon 的 `CategoryIcon.data`（bytea），**这是「图片只存网址」的唯一破例**，理由见下面那段 |
| （无单独接口） | 孤儿图标清理 | 没人引用的图标由服务端**自己对账**删掉，挂在 `/categories/batch` 和 `DELETE /categories/:id` **之后**——备份是先传图后推分类，挂在传图那一刻扫会把刚上来的图当场删掉 |
| GET/POST | `/accounts` | 账户：查 / 新建。POST 同样收 `id` 并 upsert |
| PUT/DELETE | `/accounts/:id` | 账户：改 / 删 |
| GET | `/sync/summary` | 恢复前先问一句：云端有多少笔账、多少个分类、上次上传是什么时候。重装后那句「云端有 1,284 笔账单，要恢复吗」靠它，不用先拉几百 KB |
| GET | `/sync/bundle` | 恢复用：一次返回这个用户的全部数据（分类、自定义分类图标的图片本体、账户、交易、转账、周期规则），**结构跟导出的备份文件完全一样**，所以手机端的恢复只有一套代码。图标只在这里回，没有单独的「下载一张图」接口——需要它们的时刻只有重装后那一次恢复，而那时本来就要拉整包 |
| GET | `/accounts/:id/balance` | 算这个账户现在有多少钱 |
| GET | `/transactions?from=&to=&categoryId=&accountId=&type=` | 查账单，可按时间/分类/账户/收支筛 |
| POST | `/transactions/batch` | 同步用：一次推一批本地还没同步的账 |
| PUT/DELETE | `/transactions/:id` | 改 / 删一笔 |
| GET/POST | `/recurring-transactions` | 周期规则：查 / 新建 |
| PUT/DELETE | `/recurring-transactions/:id` | 周期规则：改（含暂停）/ 删 |
| POST | `/transfers/batch` | 同步用：一次推一批转账 |
| GET | `/transfers` | 查转账 |
| GET | `/stats/summary?month=` | 月度收支总览（电脑端画图用） |
| GET | `/stats/by-category?month=` | 按分类汇总（画饼图用） |

图片分两类，去处不同：**账单收据照片**不走自己的后端——手机直接传到 Cloudinary，拿到网址后跟着那批交易一起推上去；**分类图标**的二进制直接存 Neon（见上面那两个接口）。分界线是量：收据张数无上限、单张 MB 级；图标缩完 10–20 KB、张数是个位数，为它接一个图床要多一套凭证、多一个会过期的外部依赖、多一条删不干净的清理链。

## 5. 同步、备份、恢复

数据一共有三个去处，前两个是「送出去」，第三个是「读回来」。

| | 云端（Neon） | 完整备份 `.json` | 表格 `.csv` |
|---|---|---|---|
| 什么时候用 | 换手机、重装，能上网 | 没网、服务器睡了、账号进不去 | 给人和 Excel 看 |
| 怎么触发 | 点「备份到云端」，或按用户设的周期在 App 打开时自动 | 点「导出成文件」（没法自动，要弹系统分享面板） | 同左，格式选 CSV |
| 分类怎么带 | 整张表，含所有内置的 | 同左，一起写进文件 | 只写名字路径 `餐饮 / 晚餐`，没有 id |
| 还包含 | 账户、转账、周期规则、账单图片 URL、自定义分类图标的图片本体 | 同左 **＋ 月预算** | 日期、金额、分类、账户名、店名、地点、备注、标签 |
| 幂等靠什么 | 记录 id（手机生成的 UUID） | 同左，导两次不会变两倍 | 无 id，靠「日期+金额+标题」判重，会误判 |
| 救不了什么 | 预算、主题、布局；还没备份过的账 | ——（这台手机上的全都在） | 层级以外的细节 |

### 自动同步

- **默认关**。用户在「我的 → 自动同步」里自己开，周期自己选：关 / 每天 / 每 7 天 / 每月
- **只对云端生效**。文件备份没法自动，它要弹系统分享面板让人选存哪儿
- **在 App 打开时检查**，不跑后台任务——跟周期交易补生成用同一个时机，也不用碰 background fetch
- **账单只推不拉；分类和账户是双向的**。点「备份到云端」先拉一遍云端的分类和账户合并回本地，再把本地的改动推上去。顺序不能反——先推的话本地会把云端覆盖掉，再拉就拉不到任何东西了
- **合并是三方比对，不是"谁后到谁赢"**。比的是「本地 / 云端 / 上次同步时那份（base，存在 `syncedFingerprint` 里）」：本地没动过而云端变了 → 采用云端；本地动过而云端没动 → 留着等推送（这不是冲突，不声张）；**两边都动过 → 保留本地并点名告诉用户**，因为用户正拿着这台手机，把他眼前的东西换掉比"另一台的改动这次没生效"更难解释。没有用 `updatedAt` 比新旧：服务器上 Category / Account 根本没这一列，而且客户端的钟不可信
- **三种判不了、于是一律不动的**：① 本地有、云端没有（可能是新建的，也可能是云端删了——服务器没墓碑表，分不出来，按新建处理）；② 云端有、本地墓碑里也有（本地删过，别让它自己长回来）；③ base 为空（从没推过）时退回布尔 `synced`，再退回"还是不是出厂的样子"
- **「还没备份过」有两套判据**。账单、转账、周期规则看布尔 `synced`（动过就是 0）；**分类和账户看内容指纹** `syncedFingerprint`——推送成功时把那一行的内容拼成一个串存下来，之后现算一次跟它比。理由是布尔记的是"动过没有"而不是"跟云端不一样"：把一个分类改名再改回来，布尔停在 0，备份层就永远显示「要上传的分类 1 条」，而那一行跟云端一模一样。只给这两张表做，是因为它们各几十行（现算的开销可以忽略），而"改一圈又改回去"也只在它们身上真会发生。指纹比的是**上次推上去的那份**，不是服务器此刻的状态——真去问服务器要联网，而备份卡是纯离线的
- **自定义分类图标先于分类上去**。顺序跟恢复时「先落图后写库」是同一条道理：两者凑不成一个原子操作，只能挑错得轻的那一边——先图后行，崩在中间留下的是一张没人引用的图；反过来是云端一行分类指着一张不存在的图。传哪几张由 `GET /category-icons` 的实际情况决定，所以这条路会自己愈合：某次传失败，下次备份自动补上。一张图都没有的用户一个请求都不多发
- **失败必须看得见**。没网、凭证过期、服务器睡着都会失败：记下 `lastSyncError`，不阻塞启动、不弹东西、不原地重试，下次打开 App 再试。唯一的呈现是「我的」页那张备份卡和自动同步页上的一行
- **「立即备份」和自动走同一个函数**（`pushUnsynced()`），自动那条只是先过一道周期判断

### 恢复

- **入口有两个**：重装后首次登录时问一次（本地库是空的 + 云端有数据才出现），以及「我的 → 恢复」随时手动
- **来源有两个**：`GET /sync/bundle` 或用户选的备份文件。两者是同一个 JSON 结构，所以后面三步完全共用
- **三步不能跳**：预览（干跑，数全算好但一条没写）→ 分类对照（只有对不上时才出现）→ 落库
- **账单只增不删**。本地已有的账单一条都不动；`id` 已存在的跳过（幂等）
- **分类走跟备份同一套三方合并**。包里有、本地也有同一个 id 的：本地那一行自上次同步以来没动过 → 按包里的版本更新（A 机换了图标、B 机恢复后能跟着变）；**本地动过 → 原样保留**，它仍然是「未备份」，下次推送会把本地那份送上去。所以"本地改了一堆还没备份、却先点了恢复"不会丢东西——两边并在一起，本地的那几条照样推得上去
- **分类怎么落地**：内置分类按固定 id 直接对上（改过的名字、停用状态一起回来）；自建分类 id 原样建出来；CSV 或两台手机合并这种「只有名字」的情况，按「收支类型 + 父分类路径 + 名字」匹配，匹配不上的交给用户在对照页指定
- **从文件恢复进来的记录一律 `synced = 0`**，等下次备份再推上去。就算这些账以前推过也不会变两份——服务器按 id 幂等去重。**从云端恢复的则标成已备份**（分类和账户连指纹一起写）：那份包就是服务器此刻的样子，再推一遍是白跑一趟

### 只存在手机本地、不上传的东西

月度总预算、主题、首页布局、搜索历史（`searchHistory`），以及这四个同步状态键：`autoSyncPeriod`（默认 `off`）、`lastCloudBackupAt`、`lastFileBackupAt`、`lastSyncError`。都放在本地那张「设置表」里。

还有两样：**汇率缓存**（`exchange_rates` 表，一行一个外币，记「1 MYR 换得到多少」）和 **Wise API token**（存 SecureStore，跟 Neon 连接串一个待遇）。

两样都不上传也不进备份包，理由不同：汇率缓存的每一行都能重新拉一次，而且拉回来的比备份里那份新——真正要留住的「当时用的是哪个汇率」已经存在每一笔账自己身上了；token 则是一条能动钱的凭证，而备份文件是用户会往聊天窗口和网盘里丢的东西。

**周期交易怎么补生成**（App 打开时跑）：

```
对每条启用中的规则：
  只要「下次该生成的日期」已经到了、而且没超过结束日期：
      本地创建一笔账（标记成还没同步，日期用那个日期）
      把「下次该生成的日期」往后推一个周期
  存回新的日期
```

这样长期不打开 App，再打开时会把欠的账一次补齐。
